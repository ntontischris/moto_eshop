# Product images: evacuate off the legacy origin to Supabase Storage (`images_cdn`)

Product photos are still served from the old eshop `www.motomarket-shop.gr` — their URLs live in `products.images` (sourced from the `onlyriders.xml` feed) and are fetched at request time through the same-origin [Image proxy] because the old eshop 403s the Next.js optimizer. That origin is slow **and temporary**: it will be decommissioned, taking both the images *and* the feed with it. We therefore treat mirroring as a **one-time evacuation**, not a perpetual optimization: a re-runnable, idempotent script (`scripts/mirror-images.ts`, storage path = `sha1(sourceUrl)` so re-runs skip what already exists and only fill gaps) downloads each image, re-encodes it to a single WebP, uploads it to Supabase Storage, and records the result in `products.images_cdn`. The storefront prefers `images_cdn` and falls back to the legacy image via the proxy only while `images_cdn` is `NULL`.

The proxy and the legacy `remotePattern` are a **transitional safety net, not a permanent layer** — they are removed at the legacy-decommission cutover (alongside the move to the final Supabase project and the Odoo ERP integration), once a verification report confirms ~100% coverage and a replacement image source exists for newly-ingested products. They stay until then because the same legacy host is still the source of new products via the feed. Because the mirror script is idempotent and infra-agnostic, the project migration to the final Supabase is just a re-run against the new bucket — no rework.

Considered and rejected: a **permanent proxy fallback** (keeps a slow, dying origin on the critical path forever); **on-demand mirror-on-first-request** (any image not viewed before the origin dies is lost — unacceptable for an evacuation); **pre-generating multiple fixed sizes** at backfill (YAGNI — the Next.js optimizer already produces a responsive srcset from a Supabase URL on demand).
