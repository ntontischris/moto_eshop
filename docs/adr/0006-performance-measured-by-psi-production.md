# Performance success is measured by PageSpeed Insights on production, not the preview gate

The Velocità homepage carries a Lighthouse CI gate (issue #39, `lighthouserc.cjs` + `.github/workflows/lighthouse.yml`) that runs `treosh/lighthouse-ci-action` against each **Vercel preview** deployment with `throttlingMethod: 'simulate'` (Lantern), asserting `performance >= 90`, `LCP < 2500ms`, `CLS < 0.1` on the median of 3 runs. It is tempting to read a green gate as "the page is fast" and a red gate as "the page is slow". Neither is reliable, and conflating the two repeatedly wasted effort chasing the wrong signal.

Two facts force a separation between *the gate* and *the definition of done*. First, the gate measures **preview**, not **production** — a passing or failing preview says nothing directly about what real visitors get. Second, the gate's number is **simulated and noisy**: on the same build, three consecutive runs scored `0.43 / 0.71 / 0.75`, and the Lantern-simulated LCP (~6.3s) is roughly 3× the *observed* LCP (~2.3s, the hero poster downloads in ~190ms and paints at first paint). The simulated value models a critical-chain bottleneck (CSS / fonts / hydration render delay), which is useful as a *regression detector* but is not the time any real device experiences.

**Decision:** the authoritative measure of performance success is **PageSpeed Insights run against the production URL** — its lab score for the "≥ 90" target and its field (CrUX) data for what users actually experience, which is also what Google uses for SEO. The Lighthouse CI preview gate is retained as a **pre-merge guardrail** that catches gross regressions before they reach production; it is not the success criterion, and a noisy red on a preview does not by itself block a release when PSI on production is healthy.

Considered and rejected: **treating the preview gate as the success criterion** (measures the wrong environment with a noisy, pessimistic simulation — drives work toward a number no user sees); **relying only on local Lantern runs** (the developer machine is even noisier than CI — see the #71 commit notes); **field/CrUX data alone** (lagging, 28-day-windowed, and unavailable for low-traffic pages or fresh deploys, so it cannot gate day-to-day work).
