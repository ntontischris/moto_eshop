# Storefront CSS: migrate the monolithic `components.css` to colocated, render-budget-aware styling

The storefront's visual design lives almost entirely in one hand-written file, `src/app/[locale]/(store)/_styles/components.css` — **10,990 lines / 256 KB** of `v3-*` rules — imported at the shared `(store)/layout.tsx`, so it is a **render-blocking stylesheet on every store route**. Three styling systems coexist incoherently: Tailwind (`globals.css` imports `tailwindcss` + shadcn), exactly **one** colocated CSS Module (`chat/chat.module.css`), and this monolith carrying the other 64 components. The monolith is the root cause behind the issue #71 / homepage LCP problem: on a slow-4G profile the ~114 KB of render-blocking CSS clogs the connection, and the LCP hero image — despite `preload fetchpriority="high"` — cannot **start** downloading for ~2.93 s (measured PSI "resource load delay"; render delay itself is only ~190 ms). It is also a maintainability hazard: a single cascade-order-dependent file no one can safely edit.

A prefix→usage audit (recorded in `docs/css-architecture-migration-plan.md`) shows the home page genuinely uses **~85%** of the file (hero, rails, ride-selector, gear-tunnel, editorial, offers, social-proof, brands, plus the shared `commerce/` card styles its product rails render). Only **~10–15%** is route-exclusive to checkout / PDP / PLP, and the cart styles are split between a **global** slide-over drawer (`v3-cart-panel-*`, rendered by the shell on every page) and the dedicated `/cart` page. This means **route-scoping alone is necessary but not sufficient** for home LCP: most of what loads on the home page is the home page's own CSS.

**Decision.** The destination architecture is **colocated, component-owned CSS** (the `chat.module.css` pattern applied throughout), reached by an **incremental strangler-fig migration — never a big-bang rewrite**. Two distinct levers, applied together over the migration:

1. **Route-scoping** — move route-exclusive rule blocks (checkout `v3-co/green/gutter`, PDP `v3-atc/bb/pdp/size`, PLP `v3-fs/mfd`, and the non-drawer `/cart` page styles) out of the shared import into the segments that use them, so other routes' CSS stops loading render-blocking on the home page.
2. **Render-budget awareness (the real home-LCP lever)** — keep only **above-the-fold** styling (the hero) on the render-blocking critical path; below-the-fold home sections (rails, tunnel, editorial, offers, social-proof, brands, newsletter, trust) load their CSS **non-render-blocking** (via `next/dynamic` section components and/or critical-CSS extraction), so the hero image is no longer queued behind ~85% of the page's styling on the slow-4G pipe.

Each migration slice is one section/component: extract its `v3-*` block to a colocated stylesheet, decide global vs route vs above/below-fold, cover with a test asserting the home critical CSS no longer contains moved prefixes, verify visually on a preview, and re-measure PSI. The monolith shrinks toward zero with the app never broken and every slice individually shippable and measurable.

Considered and rejected: **big-bang rewrite to CSS Modules or Tailwind** (the classic "second-system" anti-pattern — discards months of accumulated cascade fixes as fresh bugs, freezes feature work, and is impossible to visually verify in one diff; unacceptable under the active delivery contract); **route-scoping only** (fixes ~15% — leaves the dominant home-own render-blocking CSS, so home LCP stays red); **leaving the monolith and only patching images/preloads** (already done in #71 — the load-delay proves the CSS pipe contention is the ceiling).
