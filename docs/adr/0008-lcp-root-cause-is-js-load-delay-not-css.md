# The home LCP ceiling is JS bandwidth-contention (the eager chat chunk), not render-blocking CSS

Issue #71 — the slow mobile LCP on the Velocità home page — was attributed to render-blocking CSS for months (see ADR 0007, which frames the monolithic `components.css` as "the root cause behind the issue #71 / homepage LCP problem"). That framing drove the CSS strangler-fig migration (slices S5a–S5d, #86–#89) and the dead-code removal in #104. The CSS work was correct and worth doing, but a direct PageSpeed Insights measurement on production (the authoritative metric per ADR 0006) shows it was aimed at the secondary lever, not the dominant one.

**What the production PSI breakdown actually shows.** On the mobile profile the LCP element is the hero `<img>`, and its time decomposes as: TTFB ~0ms · **Load Delay ~1,240ms (dominant)** · Load Time ~40ms · **Render Delay ~250ms**. The hero is already preloaded `fetchpriority="high"` in `<head>` (verified live: the preload tag sits at byte ~196, well before `</head>` at ~5,477), so this is not a discovery/preload problem and not an image-bytes problem — load time is only 40ms. Render delay — the part CSS and fonts gate — is only ~250ms. The overwhelming cost is **load delay**: the hero's bytes are queued behind other downloads on the throttled mobile pipe and cannot *start* for ~1.24s. The biggest reducible mass on that pipe is **unused JavaScript (~122KB gz)**, dwarfing the ~250ms render-delay that CSS could buy back.

**The primary culprit is the eager AI chat chunk.** `ChatMount` is a *static* import in `(store)/layout.tsx`, so although it is wrapped in `<Suspense>`, its JavaScript ships in the initial bundle — `<Suspense>` defers *render*, not *download*. The chat client pulls `@ai-sdk/react` (`useChat`) and `ai` (`DefaultChatTransport`) through `chat-mount → chat-mount-client → chat-provider`. A fresh production build size-matches this chain to PSI's flagged chunks: the chat chunk is ~563KB raw / **~138KB gz** ≈ PSI's reported 134KiB chunk with **96.9KB unused**, and the shared-runtime chunk (~70KB gz) matches PSI's second flagged hash with 25.3KB unused. So of the ~122KB unused JS, **~97KB is the chat alone** — ~80% of the opportunity, and the lowest-risk to remove because the chat is a below-the-fold, post-interaction island that no first paint depends on.

**Decision.** The authoritative root cause of #71 is **hero load-delay driven by JavaScript bandwidth-contention on the throttled mobile pipe**, with the **eager chat chunk (~97KB gz unused) as the primary, highest-leverage, lowest-risk culprit** — not render-blocking CSS. This refines (does not reverse) ADR 0007: colocation and the strangler-fig migration remain the correct CSS *architecture*, and ADR 0006 remains the measurement law (PSI production / CrUX field, never the noisy Lantern preview gate). What changes is the **lever order** for closing #71:

1. **JS-defer (primary).** Take the chat off the initial bundle via `next/dynamic({ ssr: false })`, mounting it after idle or on first interaction (mirroring the existing `MotionProvider`/`HeroRippleProvider` gate-then-dynamic-import pattern). Expected: −~97KB gz from the initial transfer, cutting the dominant ~1,240ms load-delay.
2. **Polyfills (secondary).** Drop legacy JS polyfills via the build target (−~13.7KB).
3. **CSS (tertiary).** Continue colocation only as an architecture/maintainability goal and for the remaining ~250ms render-delay headroom — *not* as the #71 LCP fix. Aggressive critical-CSS slicing is explicitly deprioritized: the slice train already hit cascade-inversion failures at #90, and `inlineCss` is a proven dead end (breaks the build with `cacheComponents` + next-intl `<Link>`).

Considered and rejected: **continuing to treat CSS as the primary #71 lever** (aims at a ~250ms render-delay while ignoring the ~1,240ms load-delay — the measured numbers do not support it, and #90's cascade-inversion shows the cost is rising); **shrinking the chat bundle in place** (`@ai-sdk/react` + `ai` are irreducible for a working chat; the win is not shipping them on first load, not making them smaller); **deleting/disabling the chat** (it is a shipped product feature with auto-open engagement behavior — defer, don't remove); **optimizing against the Lighthouse/Lantern gate** (ADR 0006 — it is ~3× pessimistic and noisy; the same build scored 0.43/0.71/0.75, and the gate stays red by design as a live #71 scoreboard).
