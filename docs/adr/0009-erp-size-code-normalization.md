# ERP size codes are zero-padded; display strips the padding, the cart keeps the raw code

`product_stock_locations.size` stores sizes exactly as the ERP sends them, zero-padded to three characters: `00S`/`00M`/`00L` (letters), `0XS`/`0XL` (two-letter), `044`/`042` (EU shoe/boot numbers), plus legitimate combined/range sizes (`0SM`, `LXL`, `39-42`, `2-3XL`) that mean S/M, L/XL, sock 39-42, 2XL-3XL. ~94% of 17,574 sized rows follow the zero-pad rule; the rest are real combined sizes, not garbage (verified against the products they sit on — body armour, jackets, socks, MX boots).

We **strip leading-zero padding for display only** (`00M`→`M`, `044`→`44`), show anything that doesn't match the clean rule **verbatim** (`LXL`, `39-42` are already readable — we never guess where a combined size "splits"), and **send the raw [Size code] to the cart, stock checks, and the ERP**. So there are two representations of one size: the [Display size] (customer-facing, derived, never stored) and the [Size code] (authoritative everywhere else). A product whose only size row is the empty string has no [Size variant] and shows no size picker.

Considered (a) cleaning the data in the DB — rejected: the ERP is the source of truth and re-syncs would re-dirty it; (b) fully normalizing the messy tail — rejected: the tail is real combined sizes, and guessing splits risks showing wrong sizes on safety gear. This is hard to reverse because the raw-code-to-ERP contract threads through PDP → cart line → stock validation; see [ADR 0001](./0001-server-authoritative-pricing.md) for why stock/price stay server-authoritative.
