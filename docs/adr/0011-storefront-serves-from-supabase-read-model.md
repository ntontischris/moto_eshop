# The storefront serves from a Supabase read-model that the ERP feeds, and this survives the Entersoft→Odoo swap

Entersoft is the source of truth today, but the client has decided to replace it entirely with a self-hosted Odoo ERP later. Entersoft is also strained — the client already offloads half the product descriptions to a separate database to lighten it. The tempting reading is "cache everything in Supabase because Entersoft is weak," which would make the caching look like a temporary crutch to be torn out once Odoo (healthy, ours, with workers) arrives.

We treat the **Supabase catalog as the storefront's permanent read-model, fed by the ERP through the [IErpAdapter]** — the standard read-model/CQRS separation, correct regardless of how strong the ERP is. The storefront **never reads live from the ERP for browse traffic**: an ERP is a transactional system built for accounting and inventory writes, not for serving 10k products to page-view volume; serving live would couple the shop's uptime and latency to the ERP (an Odoo deploy/restart would take the shop down); and page-views ≫ stock-changes ≫ orders, so view volume must never reach the ERP, healthy or not.

What changes between Entersoft and Odoo is **only how data flows into the read-model**, and that lives isolated behind the adapter plus the sync worker. Entersoft has no webhooks, so we **poll** Public Queries on a gentle cadence (batch, to not crush it). Odoo can **push** record-change events, so the same worker becomes event-driven and near-real-time. The storefront — and everything downstream — is untouched by the swap: it is a new adapter and a new sync trigger, not a rewrite. Nothing built now for Entersoft is throwaway.

Considered (a) **live ERP reads for the catalog** — rejected for the coupling, latency and load reasons above. (b) **building a thinner cache now and a "real" architecture for Odoo** — rejected: the read-model is already the real architecture; Odoo only makes it easier (push vs poll), not unnecessary. The specific freshness policy on top of this read-model (catalog slow, stock at commit, failsafe) is [ADR 0012](./0012-stock-freshness-tiering-and-erp-failsafe.md).
