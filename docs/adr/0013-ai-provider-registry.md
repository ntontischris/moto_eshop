# AI model selection lives in one registry; the customer chatbot is pinned to OpenAI by contract, everything else is swappable

The contract (Article 6.2) names **OpenAI** specifically for the 24/7 AI chatbot. The rest of the AI surface — recommendations, price-negotiation phrasing, SEO content generation across six languages, the gift upload app — names no provider. The code already routes chat through the Vercel AI SDK (`streamText`), which is provider-agnostic, so the provider is a one-line choice rather than a hard dependency. Scattering `openai(...)`/`anthropic(...)` calls across features would make the contractual pin invisible and provider switches a find-and-replace.

We **centralize model selection in a single `ai/models.ts` registry mapping use-case → model**. The customer-facing chatbot ([Πιτ]) defaults to OpenAI to honour Article 6.2 to the letter; every other use-case picks its model from the same registry and can be OpenAI, Anthropic, or anything the AI SDK supports, changed in one place. Selection is explicit and lives in one home, so the contractual constraint is visible and the rest stays free to optimise for cost/quality.

Considered (a) **Anthropic everywhere** — rejected: diverges from the explicit "OpenAI" in the deliverable and hands a future dispute a hook, for no structural gain given the SDK abstracts it. (b) **per-feature inline provider calls** — rejected: hides the contractual pin and makes switching a sweep. This is cheap to reverse (one registry entry), but worth recording because a future reader will otherwise wonder why the chatbot alone is pinned to OpenAI while neighbouring features are not — the answer is the contract, not a technical reason.
